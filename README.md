# LeadOS

Личная CRM для поиска и ведения клиентов: Kwork, Telegram-каналы, холодный поиск по картам — одна воронка,
AI-оценка лидов и черновики сообщений. Решения и отправка — всегда за человеком.

**Как запустить и пользоваться — [docs/INSTRUCTIONS.md](docs/INSTRUCTIONS.md).** Здесь — как всё устроено.

- **Фаза 1 — ядро CRM** ✅ воронка статусов, ручной ввод, история касаний, сделки, дашборд.
- **Фаза 2 — захват из источников** ✅ API приёма лидов с дедупликацией, закладка для Kwork, чтение Telegram-каналов,
  холодный поиск по Яндекс Картам и 2ГИС с проверкой сайтов и списком обзвона.
- **Фаза 3 — AI** ✅ оценка лидов с тревожными признаками, отклики, скрипты звонков, follow-up, дайджест.
- **Деньги и повторные продажи** ✅ оплата целиком и частями по графику, чаевые, доп. опции (в т.ч. подбор AI),
  напоминания о рекомендациях и доработках, «кто порекомендовал».
- **Уведомления, импорт, готовность к Vercel** ✅ утренняя сводка и горячие лиды в Telegram, импорт истории из таблиц,
  закладка для любой страницы, выполнение AI без воркера на Vercel, cron, проверка окружения, защита входа.
- **Фаза 4 — аналитика и донастройка** ✅ воронка и выручка по источникам и периодам, ниши, звонки, Telegram-каналы,
  качество AI; поправки к оценкам, которые учитываются в следующих оценках; предложения правок правил.

Стек: Next.js 16 (App Router, server actions) · TypeScript · PostgreSQL · Prisma 7 (`@prisma/adapter-pg`) · Tailwind 4 ·
Claude API (`@anthropic-ai/sdk`) · Python/Telethon для Telegram.

## Как считается аналитика

- **Воронка.** У лида есть `furthestStage` — индекс самого дальнего этапа (`NEW … WON`), до которого он дошёл.
  При переходе в `LOST`/`SKIPPED` он не уменьшается, поэтому проигранный на переговорах лид честно учитывается
  в этапах до переговоров. Конверсия = дошли до этапа / дошли до предыдущего.
- **Зависшие лиды.** `CONTACTED` или `NEGOTIATING` без движения дольше `STALE_DAYS` дней (по `lastActivityAt`,
  который обновляют смена статуса и любая запись в истории), плюс любые незакрытые лиды с наступившей датой `followUpAt`.
- **Срок закрытия** — от `Lead.createdAt` до `Deal.closedAt`. При переводе в `WON` сделка создаётся/закрывается автоматически,
  сумму вписываешь в карточке.

## Отличия от черновика схемы

- `contactEmail` — для холодных писем.
- `furthestStage`, `lastActivityAt`, `followUpAt` — для воронки и напоминаний (см. выше).
- `onDelete: Cascade` у `Activity`/`OfferDraft`/`Deal`, индексы по `status`, `source`, `lastActivityAt`.
- `Deal.stage` по умолчанию «Старт».

- AI (фаза 3): у `Lead` — `aiVerdict`, `aiAssessment` (полный ответ оценки), `scoredAt`; у `OfferDraft` — `notes`, `model`,
  `updatedAt`; новые `PortfolioCase`, `AiJob`, `AiCall`, `Digest`.

## Где работает: Vercel и VPS

Один код, два режима ([docs/INSTRUCTIONS.md § 13–14](docs/INSTRUCTIONS.md#13-деплой-на-vercel)).

| | Vercel (сейчас) | VPS (Docker Compose) |
|---|---|---|
| AI-задачи | сразу после запроса, создавшего лид (`after()`, [src/ai/inline.ts](src/ai/inline.ts)) + ежедневный cron | сервис `ai-worker` ([src/worker/ai.ts](src/worker/ai.ts)) |
| Ежедневные дела | `vercel.json` → `/api/cron/daily` (Bearer `CRON_SECRET`) | планировщик воркера раз в минуту |
| Telegram-каналы | воркер запускается вне Vercel | сервис `telegram` (профиль) |
| База | облачный Postgres, пулинговый `DATABASE_URL`, `DIRECT_URL` для миграций, пул 3 | контейнер Postgres, пул 10 |
| Сборка | `pnpm build:vercel` (миграции + build) | standalone-образ + одноразовый `migrate` |

Общее для обоих ([src/lib/daily.ts](src/lib/daily.ts)): дайджест, follow-up, досчёт очереди, утренняя сводка — идемпотентно,
повторный запуск в тот же день ничего не дублирует. Все календарные расчёты — в `APP_TIMEZONE`
([src/lib/time.ts](src/lib/time.ts)), независимо от пояса сервера (на Vercel это UTC).

**Надёжность и безопасность:** Basic Auth на весь интерфейс ([src/proxy.ts](src/proxy.ts)) с блокировкой IP на 15 минут
после 10 неверных попыток (IP из `X-Real-IP` или последнего адреса `X-Forwarded-For` — первый клиент может подделать),
пароли в UTF-8; `/api/*` — Bearer-токены; `/api/health` для мониторинга; страницы ошибок с «Повторить»;
проверка окружения при старте ([src/instrumentation.ts](src/instrumentation.ts)) и на странице «Настройки»;
длинные действия (AI, импорт) с `maxDuration = 300`; демо-сид отказывается работать на непустой и боевой базе.

## API приёма лидов

Общая точка входа для всех захватчиков (расширение Kwork, Telegram-воркер, импорт 2GIS).
Авторизация — `Authorization: Bearer $API_TOKEN` (минимум 16 символов, `openssl rand -hex 32`).
Basic Auth на `/api/*` не действует; без `API_TOKEN` API отвечает 401 на всё.

```bash
curl -X POST http://localhost:3000/api/leads \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"source":"KWORK","title":"Бот для записи","rawText":"…","sourceRef":"https://kwork.ru/projects/3123456/view","budgetMax":"до 15 000 ₽"}'
```

| Ответ | Когда |
|---|---|
| `201 { id, url, created: true }` | новый лид в статусе `NEW` |
| `200 { id, url, created: false, duplicate: true }` | такой `sourceRef` в этом источнике уже есть — ничего не меняется |
| `422 { error: "validation", message, field }` | не прошла валидация (те же правила, что у формы) |
| `401` / `400` / `413` | нет токена / битый JSON / тело больше 100 КБ |

`GET /api/leads?source=KWORK&sourceRef=<url>` → `{ exists: false }` или `{ exists: true, id, status, url }` —
чтобы расширение показывало «уже добавлен» ещё до нажатия.

Поля: `source` (`KWORK|TELEGRAM|COLD_LOCAL|MANUAL|REFERRAL`), `title` — обязательные; `rawText`, `sourceRef`, `category`,
`budgetMin`, `budgetMax` (число или строка: `"50 000 ₽"`, `"до 15000"`, `"50к"`), `contactName`, `contactPhone`,
`contactTg`, `contactEmail`, `region`. CORS открыт (`*`) — это безопасно, потому что доступ даёт только заголовок с токеном.

### Дедупликация

Уникальный индекс `(source, sourceRef)` в БД + нормализация ссылки перед записью ([src/lib/source-ref.ts](src/lib/source-ref.ts)):
`https`, без `www`, `#якоря`, utm-меток и завершающего слэша; Kwork-заказ сводится к `https://kwork.ru/projects/<id>`,
Telegram-пост `t.me/s/…` к `t.me/…`. Не-URL (например, ID места 2GIS) хранится как есть. Одновременные одинаковые
запросы (двойной клик) тоже дают один лид. Форма в интерфейсе проверяет то же самое и даёт ссылку на существующий лид.

## Закладка для Kwork

Работает на странице заказа `kwork.ru/projects/<id>` и на странице отклика `kwork.ru/new_offer?project=<id>`.

1. Закладка ([public/bookmarklet/kwork.js](public/bookmarklet/kwork.js)) синхронно с кликом открывает окно `LeadOS/capture`.
2. Берёт данные заказа из `window.stateData.wantData` страницы. На странице отклика этих данных нет —
   тогда один раз запрашивает `/projects/<id>/view` и достаёт тот же JSON из HTML (без выполнения скриптов).
   Запасной вариант — разбор вёрстки `.want-card`.
3. Окно шлёт `leados:ready`, закладка отвечает `leados:lead` с данными — только в origin LeadOS и только этому окну.
   Окно принимает данные только от `https://kwork.ru` и только от открывшей его вкладки.
4. Окно проверяет дубль (`lookupLead`), показывает форму, сохраняет через server action с той же дедупликацией.

Что попадает в лид: заголовок; описание (эмодзи Kwork `[:1f680]` и HTML-сущности раскодируются) плюс блок фактов —
бюджет и допустимый бюджет, срок, покупатель с числом проектов и % найма, число предложений, сколько осталось;
`budgetMax` = желаемый бюджет; `contactName` = логин покупателя.

Токена в закладке нет — окно работает под обычной авторизацией LeadOS (Basic Auth). Адрес LeadOS зашит в закладку
при сборке (`APP_URL` или адрес, с которого открыта `/bookmarklet`), поэтому после переезда на VPS закладку нужно
перетащить заново. Версия (хэш кода) показана на странице — по ней видно, устарела ли установленная закладка.

Если Kwork поменяет страницу, окно покажет «Не удалось прочитать заказ» со ссылкой на ручную форму.

## Telegram-каналы

Воркер на Python/Telethon ([worker/telegram](worker/telegram/README.md)) читает каналы и супергруппы от личного
аккаунта и шлёт посты в LeadOS. Вся логика — в LeadOS ([src/lib/telegram.ts](src/lib/telegram.ts),
[src/lib/telegram-ingest.ts](src/lib/telegram-ingest.ts)), поэтому каналы и слова меняются на `/telegram` без перезапуска.

- **Фильтр.** Стоп-слова отсекают пост всегда; ключевые слова нужны в режиме «по ключевым словам»
  (пустой список = брать всё). Поиск по подстроке без учёта регистра и ё/е. Посты короче 40 символов пропускаются.
  Режим канала «все посты» — для каналов, которые целиком лента заказов.
- **Из поста в лид:** заголовок — первое предложение без хэштегов; бюджет — «50 000 ₽», «до 30к», «20-40 тыс руб»,
  «оплата 15000р.»; контакт — автор сообщения в группе или первое @упоминание/ссылка t.me (не бот и не сам канал);
  в описание дописываются канал, время публикации и совпавшие слова. Ссылка на пост — `sourceRef`.
- **Дубли.** Тот же пост — по `sourceRef`; репост в другом канале — по хэшу текста без ссылок, упоминаний,
  хэштегов и эмодзи (окно 30 дней). Повторная отправка пачки не создаёт лидов и не портит счётчики.
- **Позиция чтения** (`lastMessageId`) хранится в LeadOS: у нового канала читаются последние 50 постов, дальше — только новые.
- **Список «Мои каналы»** воркер присылает сам — так добавляются и приватные каналы без публичной ссылки.

Redis/BullMQ здесь не понадобились: воркер — один долгоживущий процесс с таймером, а LeadOS обрабатывает пачку
за один запрос.

## Холодный поиск: компании находятся сами

**Автоматический поиск** ([src/lib/osm.ts](src/lib/osm.ts), [src/lib/cold-search.ts](src/lib/cold-search.ts)).
Кнопка «Найти автоматически» у ниши на `/prospecting`: город геокодируется через Nominatim (результат кэшируется
в `AppSetting`), компании берутся из Overpass API по тегам ниши (`shop=car_repair`, `amenity=dentist`, …) в радиусе
вокруг города. Пять зеркал Overpass перебираются по очереди — если все заняты, поиск честно говорит об этом
и ничего не ломает. Источник — **OpenStreetMap, лицензия ODbL**: данные можно хранить у себя при указании авторства
(оно есть на странице и в карточке каждой компании).

**Почему не Яндекс/2ГИС API.** Условия [API поиска по организациям Яндекса](https://yandex.ru/dev/commercial/doc/ru/concepts/geosearch)
запрещают сохранять полученные данные и показывать их без карты Яндекса — на любом тарифе. [Правила API 2ГИС](https://law.2gis.ru/api-rules)
(п. 4.2) тоже запрещают сохранять данные. Поэтому карты остаются ручным каналом:

1. **Телефон есть не у всех** компаний OSM. У таких в списке обзвона стоит «телефона нет — найти: Яндекс ↗ 2ГИС ↗» —
   ссылки на поиск этой компании на картах.
2. **Дополнение** — закладкой «→ LeadOS (карты)» с карточки, которую ты открыл сам
   ([public/bookmarklet/maps.js](public/bookmarklet/maps.js)). Яндекс: микроразметка schema.org. 2ГИС: `initialState`
   страницы. Если компания уже найдена автоматически, закладка **дополняет** её (телефон, сайт, часы, ссылка на карточку),
   а не создаёт вторую — совпадение по нормализованному названию и региону либо по телефону
   ([`findCompanyToEnrich`](src/lib/lead-service.ts)).
3. **Дубли**: по ссылке (`openstreetmap.org/<type>/<id>`, `yandex.ru/maps/org/<id>`, `2gis.ru/firm/<id>`), по телефону
   (все российские номера хранятся как `+7 XXX XXX-XX-XX`) и по названию + региону.

**Что происходит после поиска.** Каждой новой компании ставится задача `SITE_CHECK`, первым десяти — `COLD_OFFER`
(скрипт звонка под нишу, с задержкой, чтобы опереться на результат проверки сайта). `SITE_CHECK` не требует Claude
и выполняется даже без `ANTHROPIC_API_KEY` — очередь просто не берёт AI-задачи, пока ключа нет.

**Проверка сайта** ([src/lib/site-check.ts](src/lib/site-check.ts)) запускается сразу после добавления и кнопкой в карточке.
Один GET главной страницы (8 с, до 1,5 МБ, редиректы проверяются заново), без обхода сайта. Внутренние адреса
(localhost, 10.x, 169.254.x…) и нестандартные порты не запрашиваются. Определяет: открывается ли, соцсеть вместо сайта,
платформа (Tilda, Wix, Битрикс, WordPress…), онлайн-запись (YCLIENTS, DIKIDI, ПроДокторов…), корзина, чат/CRM-формы,
Метрика, адаптивность, HTTPS, год в копирайте.

**Оценка** — «Горячий / Тёплый / Холодный» по сумме пробелов с учётом ниши (онлайн-запись важна клинике и салону,
магазин — рознице). Причины сформулированы как аргументы для звонка. Отсутствие признака — это «не видно на главной»,
а не «точно нет»: виджеты могут подгружаться скриптами.

**Обзвон**: сначала те, кому пора перезвонить, дальше по оценке. Кнопки «Не дозвонился» (напомнит завтра),
«Перезвонить» (Контакт, через 2 дня), «Интересно» (Ответил), «Не интересно» (Проигран) пишут звонок в историю.

## AI

Весь слой — в [src/ai](src/ai). У модели нет доступа к БД и инструментов: код собирает контекст, модель возвращает
ответ строго по Zod-схеме (structured outputs), код проверяет его и сам решает, что записать.

- **Один вызов** ([src/ai/client.ts](src/ai/client.ts)): `claude-opus-5`, adaptive thinking, `effort` по задаче
  (оценка и дайджест — `medium`, тексты — `high`), `beta.messages.parse` + `betaZodOutputFormat`.
  `fallbacks: "default"` — при отказе модели запрос сервер-сайд повторяется на рекомендованной резервной модели.
  Отказ, обрезанный ответ или ответ не по схеме — ошибка, а не пустой черновик. Каждый вызов пишется в `AiCall`
  (токены, кэш, оценка стоимости, длительность, ошибка).
- **Кэш промпта.** Системный промпт = общая рамка + правила + кейсы ([src/ai/context.ts](src/ai/context.ts)) в детерминированном
  порядке, без дат и id — одинаковый для всех задач и помечен `cache_control`. Данные лида идут в сообщение пользователя
  внутри `<lead>` и объявлены данными, а не инструкциями.
- **Оценка** ([tasks/assess.ts](src/ai/tasks/assess.ts)): балл, вердикт, соответствие специализации/бюджета/объёма,
  тревожные признаки фиксированных типов с объяснением и серьёзностью, вопросы заказчику. Балл зажимается в 0–100.
  Статус лида AI не меняет.
- **Черновики** ([tasks/drafts.ts](src/ai/tasks/drafts.ts)): отклик Kwork, сообщение автору Telegram-поста, холодное сообщение,
  скрипт звонка (структура: зацепка из проверки сайта, похожий кейс, вопросы, возражения, следующий шаг),
  follow-up с учётом истории и уже отправленного. Few-shot — отправленные сообщения того же типа, сначала приведшие к сделке.
- **Дайджест** ([tasks/digest.ts](src/ai/tasks/digest.ts)): новые лиды за 24 часа по убыванию оценки + до 5 рекомендаций;
  id, которых нет в списке, отбрасываются.
- **Очередь без Redis** ([src/ai/jobs.ts](src/ai/jobs.ts)): таблица `AiJob`, забор `UPDATE … FOR UPDATE SKIP LOCKED`,
  зависшие больше 10 минут задачи возвращаются, повторы через 1 и 5 минут, после 3 попыток — `FAILED`.
  Ошибки конфигурации (нет ключа) и удалённые лиды не повторяются.
- **Воркер** ([src/worker/ai.ts](src/worker/ai.ts)): несколько параллельных обработчиков + раз в минуту планировщик
  ([src/ai/runner.ts](src/ai/runner.ts)) — дайджест после `DIGEST_HOUR` по Москве, follow-up для зависших лидов без свежего
  черновика. Без ключа только отмечает пульс. Останавливается по SIGTERM за секунды.
- **Когда что запускается.** Новый лид (`createLeadDeduped`) → задача оценки, если AI настроен и `AI_AUTO_SCORE` не `false`.
  Кнопки в карточке выполняют задачу сразу в server action, без очереди.
- **Тест** ([scripts/ai-smoke.ts](scripts/ai-smoke.ts), `pnpm test:ai`): подменённая модель, настоящая БД — постановка
  и параллельный забор задач, сохранение оценки, параметры запроса, неизменность системного промпта, порядок few-shot,
  повторы при отказе, учёт расходов, дайджест, follow-up. Качество самих текстов модели этим тестом не проверяется.

## Аналитика

Расчёты — чистые функции в [src/lib/report.ts](src/lib/report.ts) над выгрузкой лидов за период
([src/lib/report-data.ts](src/lib/report-data.ts)); проверяются `pnpm test:analytics` на синтетических данных.

- **Воронка по источникам** — по `furthestStage`, как и на дашборде, с переходом между соседними этапами.
- **Выручка** — по `Deal.closedAt` за 12 месяцев по московскому календарю, независимо от периода страницы.
- **Ниши** — рубрики компании сопоставляются со списком ниш из «Холодного поиска» по основам слов
  («продуктовый магазин» ↔ «Продуктовые магазины»), выигрывает самое точное совпадение; остальное — «Другое».
  Доля ответивших считается только среди тех, кому звонили.
- **Звонки** — по префиксу записи `CALL`, которую пишут кнопки результата звонка; ручные записи — «Другие».
- **Оценка сайта против исхода** — те же уровни, что в обзвоне; проверяет, работают ли аргументы про сайт.
- **Telegram-каналы** — канал берётся из ссылки на пост (`t.me/<канал>/<id>`, `t.me/c/<id>/<id>`).
- **Качество AI** — калибровка по корзинам балла (только лиды, по которым уже решено), совпадение вердикта с решением
  (взял в работу / пропустил), доля изменённых слов между `OfferDraft.aiText` и отправленным текстом
  (расстояние Левенштейна по словам).

Графики — HTML/CSS без библиотек: одна серия, один тон (цвет проверен на контраст в светлой и тёмной теме),
значения подписаны текстом, подсказки при наведении, у выручки есть таблица.

## Донастройка AI

- **Поправки к оценкам** (`AssessmentFeedback`): правильный вердикт и объяснение. Последние 15 уходят в промпт оценки
  вторым кэшируемым блоком `system` ([tasks/assess.ts](src/ai/tasks/assess.ts)) — основной блок с правилами и кейсами
  не меняется и остаётся в кэше.
- **Предложения правок** ([tasks/tuning.ts](src/ai/tasks/tuning.ts)): по запросу модель получает текущие правила, поправки,
  до 8 самых переписанных черновиков (AI-текст против отправленного) и калибровку, и возвращает наблюдения,
  новые тексты категорий правил с обоснованием и недостающие кейсы. Результат хранится в `AppSetting` `ai_tuning`;
  «Применить» заменяет категорию и помечает предложение применённым (повторно не применяется). Автоматически ничего
  не меняется.

## Удобство ежедневной работы

- **Навигация** ([components/nav.tsx](src/components/nav.tsx)): на компьютере основные разделы и «Ещё», на телефоне — меню ☰;
  меню закрывается при переходе без эффектов (состояние привязано к странице, на которой открыто).
- **Разбор потока:** массовая смена статуса в списке лидов ([components/bulk-select.tsx](src/components/bulk-select.tsx)) —
  каждая смена пишется в историю как одиночная; удаления массово нет намеренно. Кнопки решения прямо в дайджесте.
- **Воронка:** перетаскивание карточек между этапами (HTML5 drag and drop, [components/pipeline-dnd.tsx](src/components/pipeline-dnd.tsx)).
- **Связаться в один тап:** звонок, WhatsApp, Telegram, почта, сайт, источник ([components/contact-links.tsx](src/components/contact-links.tsx)).
- **Экспорт** ([lib/export.ts](src/lib/export.ts)): UTF-8 с BOM и «;» для русского Excel, ячейки с `= + - @` экранируются от формул;

- **Очередь AI на Vercel** догоняется не только после создания лида и по cron, но и при каждом открытии дашборда

## Деньги по сделке

Модель: `Deal.amount` (сумма за работу) + `DealAddon` (предложена / принята / отказ) + `Payment`
(`PART` — часть или оплата целиком, `TIP` — чаевые, `ADDON` — оплата опции; `dueDate` — план, `paidAt` — факт).
Расчёты — чистые функции [src/lib/money.ts](src/lib/money.ts) (`pnpm test:money`):

- договор = сумма за работу + принятые опции; получено = оплаченные части и опции; чаевые отдельно и остаток не уменьшают;
- просрочка — по календарному дню в `APP_TIMEZONE`, срок «сегодня» ещё не просрочен;
- график делит **неоплаченный остаток** по долям, округляя до сотни; остаток округления — в последнюю часть,
  сумма частей всегда равна остатку; оплаченные части при перепланировании не трогаются;
- отклонённая опция убирает свои неоплаченные платежи; удалить опцию с оплатой нельзя.

Выручка в аналитике и на дашборде — по `Payment.paidAt`. Сделки без отмеченных оплат выводятся отдельным напоминанием.
AI подбирает опции по задаче, нише и правилу «Цены и сроки» ([tasks/addons.ts](src/ai/tasks/addons.ts)) — как предложенные.
Повторные продажи: `Deal.referralAskedAt` и `upsellAt` (напоминания через 14 и 90 дней, снимаются при отправке
соответствующего черновика), `Lead.referredById` — кто порекомендовал.

## Уведомления в Telegram

Свой бот через Bot API ([src/lib/notify](src/lib/notify)): чат находится по `/start` (`getUpdates`), настройки — в `AppSetting`.
Отправка через `notifyOnce(key)`: ключ в `NotificationLog` застолбляется до отправки, поэтому параллельные запуски
не дублируют сообщение, а неудачная отправка повторится при следующем запуске (не раньше чем через минуту).
Утренняя сводка собирается только из непустых разделов; горячий лид — после оценки, если балл ≥ порога,
лид новый и создан не больше суток назад. HTML экранируется, длинные сообщения режутся по строкам.
Тест — `pnpm test:notify` (подменённый Telegram, настоящая БД).

## Импорт из таблиц

[src/lib/import](src/lib/import): разбор CSV/TSV (кавычки, переносы в ячейках, BOM, `,`/`;`/табуляция, Windows-1251),
угадывание колонок по заголовкам, нормализация сумм, дат (включая числовые даты Excel), статусов и источников —
чистые функции (`pnpm test:import`). Клиент показывает сопоставление и предпросмотр, строки уходят пачками по 200;
сервер разбирает их заново и не доверяет клиенту (`pnpm test:import-db`). Дубли по телефону, email, названию и дню
пропускаются; у пачки есть `importBatch` — «отменить импорт» удаляет её целиком. Импорт не запускает AI-оценку и не создаёт
напоминаний о рекомендациях задним числом.
